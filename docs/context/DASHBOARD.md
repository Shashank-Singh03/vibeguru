## Automatic updates

- The local server checks reports, suite records, vector definitions, activity and
  Git state approximately every three seconds. Changed snapshots notify the browser
  through server-sent events; periodic fetching provides a fallback.
- `node --watch` restarts the backend after its imported code changes. The browser
  reconnects. A frontend asset revision reloads HTML/JavaScript/CSS changes.
- Campaigns from `scripts/lab.mjs` appear while cases finish; incomplete campaigns
  remain labelled running. Missing or corrupt case reports become visible ERRORs.
- `npm test` writes a RUNNING record, native TAP output and final test counts/failure
  details. Discovery cannot silently pass when zero tests run.
- Direct `mix test` uses a test-only ExUnit formatter to persist counts, doctests,
  failures and skipped tests. Invalid setup is not treated as a skipped success.
- `npm run check` records formatting and compilation commands, runs ExUnit, then
  runs Node tests. These command checks and detailed test suites are distinct.
- Earlier-source suite records are marked stale after code changes. The fingerprint
  includes dirty code/config file stamps and HEAD, excluding documentation and
  ignored generated reports. It is a local freshness indicator, not a Git commit.
  Manually entered commands outside the supported recorders are not invented as
  passing executions. Abruptly terminated processes may leave a RUNNING record.

The dashboard updates after edits; **it does not automatically rerun tests after
each save**. Use the relevant test command, or `npm run check` for the full check.
Semantic implementation notes need intentional maintenance; the live change list
updates without a note. `AGENTS.md` makes these steps part of future agent work.

## Adding vectors

1. Implement a bounded experiment with explicit expected outcomes and retained
   evidence. Keep infrastructure failure distinct from an asserted app failure.
2. Add/update its entry in `dashboard/vectors.json`. Use `planned` until the
   capability is implemented; implementation is not proof of general validation.
3. Existing vectors have built-in mappings. New entries can supply `match` rules
   without changing the dashboard frontend or collector:

   ```json
   {
     "id": "http-recovery",
     "name": "HTTP failure & retry",
     "family": "Recovery",
     "stage": "implemented",
     "description": "A bounded failure followed by an observable successful retry.",
     "scope": "State the tested app, response fixture and recovery deadline.",
     "match": { "assertion_ids": ["retry-recovered"] }
   }
   ```

   Supported match arrays are `assertion_ids`, `signatures`, `evidence_kinds`,
   `variants`, `apps`, `app_prefixes` and `modes`. Any matching rule associates the
   case with that implemented vector. Planned entries never claim coverage even
   if a rule matches. Association means attempted scope, not independent success.
4. Run and retain a normal control, the failing condition and appropriate recovery
   or candidate verification. The dashboard discovers the saved campaign.
5. Append a concise change/evidence note to `dashboard/activity.json`, update the
   context document, run relevant checks and refresh the repository context graph.

## Timing analytics — 11 October 2026

The Changes view now includes full repository-check wall time, latest stage logs
and median/p95 per command. `scripts/checks.mjs` records the parent full check;
its duration is not the sum of parent and nested Node/ExUnit history. Repository
Elixir runs carry explicit scope; older or focused runs without scope are grouped
by their test count and marked unknown. Failed executions remain visible.

Browser timing samples require complete independently assessed measurements and
journeys. A FAIL can also contain incomplete work, so verdict alone never qualifies
a timing sample. Samples are grouped by application, scenario and cycle count.
Missing duration and running suites are excluded. Small local samples and mixed
historical versions are not latency guarantees. See [TEST_TIMING.md](TEST_TIMING.md).
